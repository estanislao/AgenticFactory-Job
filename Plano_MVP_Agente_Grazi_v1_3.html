O que é. Grazi é a agente de coordenação da operação: o gestor e o diretor conversam com ela por DM no Microsoft Teams e recebem status, atrasos e insights sobre um projeto, cruzando o que está planejado (Microsoft Planner) com o que foi de fato desenvolvido (GitHub). No MVP ela acompanha um único projeto — o What-Connector — mas é construído de forma que adicionar projetos seja configuração, não código.

4,5 diasde seg 21/09 a sex 25/09, 12h
1 projetoWhat-Connector (Planner + repo GitHub)
3 integraçõesTeams (canal) · Planner e GitHub (leitura)
0 escritasagente 100% consultivo no MVP

Cinco decisões que cabem no prazo

  1. Mesmo runtime do Marcel (OpenClaw). O canal Teams é nativo do framework — o que mais custou tempo no Marcel (bot no Azure, proxy, publicação) vira repetição de receita conhecida, não descoberta. A Grazi é um workspace novo com seu próprio AGENTS.md, cases/ e skills/.
  2. Somente leitura. Nenhuma skill de escrita existe no código. Sem gate de confirmação, sem risco de ação indevida — o maior custo de engenharia do Marcel simplesmente não entra.
  3. Snapshot em disco, não API ao vivo. Um cron sincroniza Planner e GitHub a cada 15 min num snapshot.json por projeto; as consultas leem o snapshot. Respostas rápidas, sem estourar rate limit, e a agente nunca "vê" um número que o código não calculou.
  4. Insight é código, narrativa é LLM. Os KPIs (atrasos, carga por pessoa, aderência de etapas) são calculados em Python determinístico; o modelo só redige a resposta a partir do JSON. Anti-alucinação por construção.
  5. Multi-projeto desde o primeiro commit. Tudo é indexado por project_id (config, snapshot, skills, cache). Um segundo projeto entra com uma entrada nova no projects.yaml.
Caminho crítico está fora do código. Azure AD (app + bot + permissão de Planner com consentimento de admin) e a publicação do bot no Teams dependem de terceiros e travaram o Marcel por dias. Como o canal Teams (E2) fecha já na terça, esses pedidos precisam sair hoje, segunda-feira, ainda de manhã. O plano B (seção 5) garante deploy na sexta mesmo se o admin do tenant atrasar. A seção 7 lista o que copiar do Marcel para o canal não ser construído do zero.

1.3 Contratos que fixam o escopo

Perguntas que a Grazi responde (MVP)

  • Como está o projeto? (progresso por bucket, % concluído, resumo)
  • O que está atrasado? (lista, dias de atraso, responsável)
  • O que a pessoa X tem / atrasou? (carga e atrasos por colaborador)
  • O que vence esta semana / até <data> / no período?
  • O que foi concluído desde <data>?
  • As etapas foram desenvolvidas a tempo? (Planner × GitHub)
  • O que aconteceu no repositório nos últimos N dias?
  • Quais são os principais riscos / insights de gestão agora?

Regras de resposta (red lines)

  • Só reporta o que veio no JSON da skill; sem número, diz "não tenho esse dado".
  • Toda resposta carrega a hora do snapshot ("dados de 10h45").
  • Sem escrita: não cria, edita, atribui nem comenta em Planner ou GitHub.
  • Fora do projeto cadastrado → "fora do meu escopo nesta fase".
  • Fonte indisponível → informa a indisponibilidade e responde com o último snapshot, marcado como tal.
  • Nunca responde "sem mudanças" sem ter chamado a skill nesta invocação.

Status de tarefa (Planner) — definição única no código

StatusRegra (campos do Graph: percentComplete, dueDateTime, completedDateTime)
Concluída no prazopercentComplete = 100 e completedDateTime ≤ dueDateTime (ou sem prazo)
Concluída com atrasopercentComplete = 100 e completedDateTime > dueDateTime
No prazonão concluída e dueDateTime ≥ hoje
Atrasadanão concluída e dueDateTime < hoje (dias de atraso = hoje − prazo)
Sem prazo / sem responsávelausência de dueDateTime / de assignments — reportadas como risco de gestão, não como atraso

Vínculo Planner ↔ GitHub ("etapa desenvolvida a tempo?")

Duas convenções, ambas configuráveis no projects.yaml, resolvidas nesta ordem:

  1. Tarefa → issue/PR: o título ou as notas da tarefa contêm #123 ou a URL de uma issue/PR. Etapa "a tempo" = issue fechada ou PR mesclado até o dueDateTime.
  2. Bucket → milestone: bucket do Planner com o mesmo nome de um milestone do GitHub. Aderência = % de issues do milestone fechadas × prazo do bucket (prazo = maior dueDateTime das tarefas).
  3. Sem vínculo: a Grazi informa que não há vínculo e responde só com a atividade do repositório (commits/PRs por autor no período). Não infere.
Decisão de hoje com o gestor. Qual convenção a equipe do What-Connector já segue (ou passa a seguir a partir de terça). Sem isso, a pergunta 6 responde "sem vínculo" — o resto do MVP não depende dela.

1.5 Pronto para multi-projeto (fase 2) sem retrabalho

  • Toda skill recebe --project; nada é hard-coded. Com uma única entrada no projects.yaml, o handler assume o default; com várias, o AGENTS.md pergunta "qual projeto?" ou aceita o nome na frase.
  • Snapshot, cache e evals são por project_id; um q_portfolio.py (visão consolidada) é adição, não mudança.
  • Regras de status e de vínculo têm defaults globais e override por projeto.
  • Quando o runtime da Factory (agent.yaml / SOUL.md / tools.yaml do plano-base) estiver pronto, o AGENTS.md vira SOUL.md e as skills viram tools declaradas — a lógica de negócio (src/grazi/) migra sem alteração.

1.6 Como o Claude Code entra

  • CLAUDE.md na raiz (escrito na segunda): stack Python 3.12, CLIs com argparse e saída JSON, testes com fixtures gravadas das APIs, ruff, proibido segredo em código, proibido qualquer chamada de escrita às APIs, carregar env dentro de função.
  • Uma sessão por bloco de trabalho (conector Planner, conector GitHub, insights, handlers, evals) e um PR por atividade da seção 3 — a atividade fecha quando o PR passa nos testes e é revisado por quem não construiu.
  • Fixtures primeiro: na terça, se as credenciais ainda não chegaram, o Claude Code gera fixtures a partir do schema documentado do Graph e do GitHub; a troca pelo dado real é só apontar a env.
  • Evals como teste de aceitação: os 20 casos YAML são escritos pelo Claude Code a partir das perguntas do gestor e rodam no CI a cada PR (padrão da Factory: falhou, não mescla).

Paralelismo que faz o prazo fechar. O time é só o Desenvolvedor e o PM — não há uma pessoa de infra separada. Na terça, o Desenvolvedor intercala código (E1) e configuração de Azure/servidor (E2) no mesmo dia; é por isso que o canal Teams é montado a partir do kit do Marcel (seção 7), não do zero — sem esse atalho, uma pessoa só não fecha as duas etapas na terça. Na quarta, E3/E4 (produto) e o início de E5 (evals e cron) seguem em sequência, não em paralelo. A quinta fecha a qualidade e já faz o deploy técnico em produção, para que a sexta seja só validação pelo PM e pelo diretor, e go-live.

3Atividades

Time enxuto de duas pessoas constrói a Grazi: DEV Desenvolvedor — todo o código e toda a infra (Claude Code, Azure, servidor, credenciais técnicas) · PM Gerente de projeto — escopo, dados, acessos de negócio e validação. Regra de gate da Factory, adaptada ao time de dois: quem valida uma atividade é sempre o PM, nunca o DEV que a construiu. Não confundir com "gestor" e "diretor" nas tabelas abaixo: são os usuários finais da Grazi no What-Connector — quem faz as perguntas pelo Teams — e não fazem parte do time de construção.

8Roadmap — do MVP consultivo ao conhecimento contínuo do projeto

O MVP responde com base em dois sistemas estruturados (Planner e GitHub). O que fica de fora — o que foi dito nas reuniões e discutido no grupo do Teams do projeto — é onde normalmente mora o risco que ninguém registrou no board. Este roadmap estende a Grazi em duas fases, na mesma ordem em que o Marcel evoluiu: primeiro ler mais fontes para enriquecer o insight, depois — só depois de validado — escrever de volta no sistema de origem.

Não é redesenho, é extensão do mesmo desenho. O MVP já separa "o que o código garante" (conectores, snapshot, insights determinísticos) de "o que o LLM decide" (narrativa, roteamento). As fases abaixo entram nesses mesmos encaixes: fonte nova → conector novo → seção nova no conhecimento do projeto → skill nova. A única peça genuinamente nova é a escrita (fase 3), e para essa o Marcel já é a prova de que o padrão funciona em produção.

8.1 Fase 2 — Conhecimento contínuo do projeto (ainda 100% leitura)

Duas fontes novas, ambas do Teams, com propósitos diferentes — a mesma distinção que o próprio documento do Marcel faz entre "canal conversacional" e "automação de reunião" (seção 4 daquele documento): uma é evento (reunião terminou), a outra é fluxo contínuo (mensagens do grupo).

Fonte novaO que a Grazi passa a fazerPadrão do Marcel que se replicaCritério de pronto
Ata de reunião do projeto (status, planning, retro — o equivalente de Discovery/Alinhamento do Marcel, mas para gestão de projeto) Você adiciona "Grazi" à reunião pelo painel de Apps (não como participante). Ao final, ela lê a transcrição do Graph, classifica o tipo de reunião, gera uma ata curta — só com o que foi dito, nada inventado — e manda para validação do PM no Teams antes de guardar em qualquer lugar. Exatamente o fluxo "Marcel nas reuniões": app pelo painel, checar transcrição ligada, reunião precisa ser encerrada de fato para gerar a transcrição, reuniões de canal não são suportadas. Mesmo aviso: "o que não foi dito fica em branco — a agente nunca inventa nem deduz". Ata chega em poucos minutos após o fim da reunião; PM confere e corrige antes de qualquer gravação.
Canal/grupo do Teams do projeto (a discussão corrente do time sobre o What-Connector) A Grazi passa a acompanhar as mensagens do canal e extrair, em segundo plano, menções a bloqueios, riscos e decisões — sem responder no canal, só indexando para consulta ("o que foi decidido essa semana?", "algum risco foi levantado no canal?"). Extensão original — o Marcel não lê canal, só e-mail vinculado ao deal. O princípio equivalente do Marcel se aplica: "mensagem que não está vinculada ao projeto não existe para a Grazi" — por isso o canal precisa ser o oficial do projeto, mesma regra do Marcel do "Teams como único canal de coordenação". Em uma amostra de 20 mensagens reais do canal, a Grazi classifica corretamente ≥ 85% como decisão / risco / irrelevante.
Camada de conhecimento do projeto (nova, sustenta as duas fontes acima) Um connectors/teams_knowledge.py (Graph: callTranscripts + mensagens de canal) grava ata e trechos relevantes por project_id, com fonte e timestamp — mesma lógica de fila em disco do webhook de transcrição do Marcel, para isolar falha de extração sem perder o evento original. Padrão "fila em disco, processa em cron separado" do transcript_process.py do Marcel — webhook só grava rápido, quem processa é outro processo. Uma skill q_conhecimento.py responde "o que foi decidido essa semana" citando a reunião ou a mensagem de origem — nunca uma afirmação sem fonte.

8.2 Fase 3 — Escrita controlada no Planner (paridade com o Marcel → Pipedrive)

Só entra depois da fase 2 estabilizada. O Marcel já resolveu, em produção, o problema central de dar a uma agente permissão de escrever num sistema de gestão sem virar risco — a Grazi replica a mesma solução, trocando Pipedrive por Planner.

Capacidade novaPadrão do Marcel replicadoRed line
Propor tarefas/atualizações no Planner a partir de uma ata ou de uma decisão do canal ("posso criar 3 atividades: X, Y, Z — responsável a definir em 1") Skill de escrita isolada da de leitura — no Marcel, pipedrive_write_skill.py é a única com update_deal/add_note/create_activity; o resto do código só lê. Na Grazi, uma planner_write_skill.py nova, com só create_task/update_task/add_comment — sem excluir. Toda skill de leitura continua proibida de escrever, mesmo depois da fase 3 existir.
Confirmação por palavra curta, no mesmo vocabulário do Marcel "ok" → cria a atividade; "feito" → a Grazi confere no Planner antes de marcar concluída (nunca confia na palavra sozinha); "não faz sentido porque..." → não grava e ajusta a próxima sugestão. Reaproveitar o vocabulário mantém a experiência igual à que o time já aprendeu com o Marcel. Resposta fora desse vocabulário não é interpretada como confirmação — silêncio ou ambiguidade nunca vira escrita.
Gate de confirmação verificado em código, não só pedido no prompt A mesma evolução que o Marcel já fez: de "instrução de texto" (frágil, a agente podia pular) para um confirmation_gate.py — token de uso único e com prazo, gerado fora do agente no momento em que a proposta é enviada, verificado antes de qualquer chamada de escrita. Escrita sem token válido é recusada pelo código — o LLM não decide se pode escrever, só propõe.
Sinalizar "responsável a definir" quando a ata ou a decisão não tem dono claro Mesmo alerta do Marcel para atividades sem responsável — nunca cria tarefa órfã silenciosamente. Toda proposta sem responsável aparece destacada na mensagem de validação, nunca escondida numa lista.
Escopo de quem pode confirmar escrita Mesmo princípio de privacidade do Marcel ("você vê só os seus deals; Sergio e Marcus têm a visão do time") — na Grazi, só quem está no allowFrom do projeto confirma escrita nele. Pedido de escrita vindo de fora do allowFrom é recusado, não escalado silenciosamente.

8.3 Sequência e gate entre as fases

  • Fase 2 não entra no MVP de sexta — é a próxima onda, logo após o go-live, com o What-Connector já servindo de piloto real (mesma lógica do plano-base: interações reais primeiro, evals depois).
  • Fase 3 só abre depois que a fase 2 estiver estável — sugestão de critério: pelo menos duas semanas de atas e leitura de canal em produção, com o PM validando manualmente cada ata sem achar erro relevante. Escrita é o único ponto da Grazi onde um erro sai do chat e vira dado errado em outro sistema; o mesmo cuidado que levou meses de maturação no Marcel antes de escrever no Pipedrive se aplica aqui.
  • Gate verificado por quem não construiu — mesma regra da Factory usada no MVP: a decisão de abrir a fase 3 é do PM, não do Desenvolvedor que a implementou.
